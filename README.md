# Game Nation

Game Nation is a Vite multi-page site using Supabase Auth, PostgreSQL, RLS, and Realtime. The homepage is a simple entry point for Quick Booking, games, and login; `quick-booking.html` supports anonymous guest slot reservations.

## Local setup

1. Copy `.env.example` to `.env` and set `VITE_SUPABASE_PUBLISHABLE_KEY` to the project's **publishable** key. The Supabase project URL is already configured in the example. The key was not included in the request, so it must be copied from the project's API settings. Never put a database password, secret key, or service-role key in this file.
2. Choose one database setup path:
   - **New Supabase project:** in the SQL Editor, run `supabase/fresh-install/USER.sql`, then `GUEST.sql`. Continue with step 3, register and confirm `dg3667610@gmail.com`, then run `supabase/fresh-install/ADMIN.sql` once to grant the admin role.
   - **Existing project:** run only unapplied files from `supabase/migrations/` in filename order. Do not also run the fresh-install bundles. Migration `202610110003_admin_initialization.sql` promotes the confirmed admin account if it already exists; if you register that account later, run that migration's admin initialization statement once.
   Both paths create the schema and security policies and provision the two initial consoles at ₹80/hour. The three fresh-install bundles are grouped by USER, GUEST, and ADMIN functionality; keep the order shown.
3. Enable Email in Supabase Authentication. Account creation supports either setting: with **Confirm email** enabled, new members receive a confirmation email and can sign in after confirming; turn it off only if you want accounts to enter the dashboard immediately. Signup confirmation uses the configured Site URL instead of requesting a separate redirect. Set the Site URL and allowlist local and production account page URLs, for example `http://localhost:5173/account.html` and `https://YOUR_DOMAIN/account.html`, for password-reset links.
4. Start the site:

   ```powershell
   npm install
   npm run dev
   ```

6. Sign into the admin dashboard, review console rates, and add the actual dates/times under **Slot availability**. No opening hours are invented or seeded.

## Security and behavior

- The browser uses only the project URL and publishable key. Every exposed table has RLS. Gamer profiles and bookings are private to their owner; the authenticated leaderboard RPC returns only gamer names, Game IDs, game tags, and aggregate play counts/duration. Admin queries require the database profile role.
- Auth-user triggers create permanent unique Game IDs and gamer profiles. The configured admin email is promoted only by a trusted database trigger after email confirmation.
- Booking inserts derive the user, status, and total from the authenticated session, selected availability row, and console rate. Admin status changes use a database RPC. A PostgreSQL GiST exclusion constraint prevents overlapping approved/completed sessions for one console, including concurrent approvals.
- Pending and rejected/cancelled requests do not reserve a slot. Completed booking totals drive spending and revenue metrics. Admin reports are queried from the database and support a date range; booking and gamer lists include search/status/date filters.
- The dashboard and status page refresh booking state through Supabase Realtime. Public visitors can read active console names and open times, but cannot read bookings or profiles.
- Tournament workflows use migration `202610110005_tournament_system.sql`. Public pages can read tournament schedules, registered names, brackets, match scores, and aggregate standings; all writes go through server-side RPCs. Registration is unique per account/event, bracket slots accept registered players only, and only admins can change tournament state, scores, or results.
- Signed-in gamers can access their private tournament points, match record, and history on `my-tournaments.html` from the animated tournament card on their dashboard. The gamer card shows available playtime without exposing the wallet's conversion rate.
- Confirmed tournament wins create versioned points transactions (10 points by default). Reconfirming an unchanged result is idempotent; an admin correction records a reversal and replacement award. Automatic byes advance without points. Result versions and point transactions are available to admins in the tournament dashboard audit panel.
- Migration `202610110001_initial_gamenation.sql` also adds gamer tags and the private gamer leaderboard alongside the profile and booking schema.
- Migration `202610110006_wallet_games.sql` adds admin-managed INR credit, a configurable credit-per-hour conversion, and the game catalog with descriptions and YouTube trailer URLs. It clears pre-existing game rows on the first upgrade from the legacy catalog schema; after applying it, admins can add games from **More games**. Gamer cards display wallet credit as remaining hours and minutes.
- Migration `202610120001_admin_live_sessions.sql` adds persistent admin live-session timers and disconnect protection. Starting an approved booking, pausing, resuming, and stopping are server-authorized; only complete minutes are charged, wallet charges are ledgered in idempotent minute checkpoints, and the booking is completed when its timer is stopped. New booking approvals reserve a slot without precharging the full slot; actual playtime is charged by the live timer. Legacy booking charges are refunded into the wallet when an admin first starts a timer for that booking. Server-persisted timer heartbeats hold the display at the last saved checkpoint during a disconnect and pause the timer when the server is reachable again. The conversion setting enforces a minimum rate of ₹0.60/hour so paise rounding cannot produce free sessions.
- Migration `202610120007_quick_booking.sql` adds Quick Book reservations and persistent admin start/pause/resume/stop timers. Migration `202610120009_admin_only_quick_booking.sql` keeps the underlying instant-reservation RPC admin-only. Migration `202610130010_guest_booking_wallet_analytics.sql` adds guest slot lookup and booking for one to three players, wallet receipts for Quick Book and slotless walk-in sessions, password-confirmed analytics reporting reset, admin Quick Start timers, and configurable Quick Book/Quick Start countdown lengths. Admins save separate timer lengths from **Data settings**; each new timer keeps the configured length it started with, and overtime is indicated without ending play automatically. The public Quick Booking page shows upcoming availability in a responsive grid and opens a booking dialog with animated player selection and a live total. Admins can start, pause, resume, and end walk-in timers in the full-screen Quick Start on **Live sessions**; ended sessions are removed from the live list.
- Admin operations are split into `admin.html` plus dedicated tournament, gamer-credit, slot/console, live-session, game-library, and data-settings pages. The admin overview shows today/month revenue, admin wallet receipts, pending requests, monthly completions, registered gamers, and slot utilization; its reset control requires password verification and resets the reporting baseline without deleting booking or wallet history. Admins can approve/reject player requests directly from its requests panel. Admin headers link only to admin destinations, with sign-out available from the session navigation.
- Migration `202610120002_admin_delete_gamer.sql` adds an admin-only account deletion RPC. The Gamers & credit page requires explicit confirmation; deleting a gamer removes their Auth/profile account, bookings, wallet history, registrations, tournament results, and points. Tournament matches involving that gamer are reset without their identity. Accounts with a running or paused live session must have that timer stopped first. Admin accounts cannot be deleted through this gamer action.
- Admin slot scheduling splits a selected start/end range into consecutive one-hour availability records; ranges that do not contain complete hours are rejected. The public booking page displays each slot's start time only, while requests use the matching one-hour interval.
- The homepage has prominent Quick Booking, Games, and Login actions. Guests can see upcoming open slots and reserve one with their name and player count from `quick-booking.html`; these Quick Book reservations are immediate and do not need approval, and receipts are recorded in the admin wallet ledger. The same page links to anonymous private-session requests in `private-booking.html`; those requests require team confirmation via WhatsApp.
- Edit the seeded hourly rates from the admin console list. Prices are calculated by the database from those rates and booking duration; values in browser requests are not trusted.

## Build and deployment

Run `npm run build`; deploy the generated `dist/` directory to a static host. Configure `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` in the host's build environment, then rebuild. Add the production account page to Supabase Auth's redirect allowlist. Do not deploy `.env` or any Supabase secret/service-role key to the static site.

For Vercel, add `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` in **Project Settings → Environment Variables** for each environment you deploy (Production, Preview, and Development as appropriate), then trigger a new deployment. These `VITE_` values are included in browser assets at build time; only the publishable key belongs there. Vercel has not been configured from this workspace.

## Verification checklist

After applying migrations and configuring the publishable key:

1. Register a new email, confirm it, sign in, and verify its profile has role `gamer`, a stable `GN-...` Game ID, and only its own booking history.
2. Sign in as the confirmed admin email and verify the admin dashboard is shown. From a gamer session, try updating the profile `role` through the Supabase API; the column grant and database trigger must reject the change. A gamer must not be able to read another profile or booking directly; the leaderboard should expose only its documented aggregate player fields.
3. As admin, schedule a range of three hours and verify it creates three one-hour slots; a partial-hour range should be rejected. As a gamer, verify the standard public page shows each slot and requests require admin approval.
3a. As an anonymous visitor, open `quick-booking.html`, select an upcoming slot, enter a name, select one to three players, and verify the total updates before booking instantly without approval. Verify a second guest cannot reserve the same slot, and its receipt appears in the admin wallet. Follow the private-booking option and verify a guest can submit a WhatsApp request that is clearly marked as requiring team approval.
3b. As admin, set separate Quick Book and Quick Start timer lengths in **Data settings**, then open **Live sessions → Quick Start**, enter a player name, choose player count, and verify its price, configured full-screen timer, pause/resume, and end controls. Confirm Quick Book uses its configured timer length. Updating settings should affect newly started timers only; timer expiry marks overtime but does not automatically end play. Quick Start does not reserve a scheduled slot, and ended sessions disappear from the live list.
3c. As admin, reset analytics and verify password re-entry is required, dashboard metrics use the new reporting baseline, and existing booking/wallet history remains intact.
4. Approve the request as admin, then attempt to approve another overlapping request for the same console. The second approval must fail at the database exclusion constraint. Rejecting/cancelling a pending request should leave the slot requestable again.
5. Complete a booking and verify completed-session, spending, revenue, and utilization figures change from database records. Verify Realtime updates another open dashboard/status page.
6. Use password reset and confirm the recovery link opens the new-password form before it routes to the dashboard.
7. On the gamer card, update the name, phone, and up to five game tags. Confirm the card shows the selected tags and that the rankings filters reorder players by completed sessions, bookings, and completed playtime while marking the signed-in player's rank.
8. As admin, create a tournament, open registration, and confirm a gamer can register only once, withdraw before the deadline, and cannot exceed the player limit. Close registration and generate a random or manual bracket; verify odd-sized entries receive byes with no points, and that a manual bracket cannot start until every registered player is assigned exactly once.
9. Start the tournament, record and confirm a result, and verify the winner advances and receives points once. Reconfirm the same score and verify points do not change; correct the winner before its next match is confirmed and verify the audit records a reversal and replacement award.
10. Verify tournament management and score RPCs reject a gamer account, while public tournament pages and Realtime updates show registration counts, current matches, confirmed results, and rankings.
11. As admin, change the wallet's credit-per-hour rate and add credit to one gamer. Verify only that gamer sees the equivalent hours/minutes on their gamer card. Approve a booking, start its live timer, and verify only complete minutes are charged; stopping the timer completes the booking.
12. As admin, add a game to Solo, Duo, or Squad and confirm it appears in the matching More Games tab. Hide it from the admin library and confirm it disappears publicly, then restore it.
13. Apply `202610120001_admin_live_sessions.sql`. As admin, open Live sessions, start an approved booking, verify the gamer wallet is charged for each complete minute while the timer runs, pause and resume it, and stop it. Confirm partial minutes are not charged, the booking is completed, the wallet ledger records the session charge, and insufficient credit stops further billed time. Disconnect the browser network and reconnect; verify the timer pauses at its last saved heartbeat and does not include the disconnected period.
14. Open Private Booking from the homepage. Verify required contact and event fields, date/time and group-size inputs, and that submitting opens a WhatsApp message containing the entered request details; confirm the page clearly states the request needs staff confirmation.
15. Apply `202610120002_admin_delete_gamer.sql`. As admin, delete a test gamer from Gamers & credit and confirm the account disappears; verify self/admin deletion and deletion during a running/paused live session are rejected, and that the account can no longer sign in.

These are live-project checks and require applying migrations, a real publishable key, and test accounts. They cannot be run from this workspace before those manual steps.

## ESP32/ESP8266 status endpoint (disabled by default)

The optional `supabase/functions/device-status` function is not deployed and is not called by the website. Keep it that way until a device rollout is ready. It accepts only `online`, `offline`, or `maintenance`, authenticates a per-device bearer token by its SHA-256 hash, looks up an enabled device, and writes only that device's own console status. The device cannot change bookings, prices, user records, or roles. RLS denies browser reads/writes to device status; status records are admin-readable.

For a future deployment, provision a random per-device token outside the repository, store only its lowercase SHA-256 hex digest in `public.devices.token_hash`, and set that device's `enabled` field deliberately. Store the raw token on the device, not in website code. Deploy the function only when needed with Supabase CLI, set `SUPABASE_SERVICE_ROLE_KEY` as an Edge Function secret, and never expose that secret to the browser. Send `POST` requests to the function with `Authorization: Bearer <device-token>` and a JSON body such as `{"status":"online"}`. Disable a device by setting `enabled = false`; do not reuse tokens across devices.
